디버거로 관찰하고, 직접 짜서 완성한 토큰갱신·로그아웃

"설계 노트 남겨줘" 요청 이후부터 지금까지의 기록. 디버거를 처음 배워서 이미 짠 코드를 눈으로 관찰하고, 그다음엔 요구사항만 받고 refresh()/logout()을 직접 작성 — 막히고, 실수 찾고, 스스로 고치는 과정까지.

회고

"코드가 어떻게 이렇게 되는지 모르겠다"

필터 코드까지 다 짜놓은 뒤, 눈으로 읽기만 해선 실행 흐름이 상상이 안 된다는 걸 인정. 코드를 읽는 것도 훈련이 필요한 기술이라는 전제로, 디버거로 실제 값을 관찰하는 법을 배우기로 함.

스킬

IntelliJ 디버거 첫 사용

브레이크포인트 + Step Over(F8)로 이미 완성해둔 signup()·login()을 한 줄씩 따라가며 직접 관찰:

  • encodedPassword가 실제로 $2a$10$... 형태로 해시되는 순간
  • new Member(...) 실행 직후 role: USER, tier: BASIC 등 기본값이 생성자 안에서 자동으로 채워지는 순간
  • accessToken/refreshToken 문자열이 실제로 조립되는 순간

"코드를 상상하지 않고 관찰하는" 방법을 처음으로 익힘.

구현

SecurityConfig에 JWT 필터 배선

JwtAuthenticationFilter를 addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)로 필터 체인에 끼워넣고, JwtAuthenticationEntryPoint를 exceptionHandling()에 연결해서 인증 안 된 접근이 403 대신 401로 응답하게 배선. 컴파일 통과 확인.

전환점

"이런 거 못하면 의미가 있나"

코드를 받아 적기만 하는 방식에 근본적인 의문 제기. 여기서부터 요구사항만 받고 직접 작성 → 막히면 디버깅 절차로 접근하는 방식으로 전환. 디버깅 5단계(재현 → 에러 읽기 → 격리 → 진단 → 수정)를 프레임워크로 정리.

직접 작성

refresh() — 막히고, 다시 시도하고

메서드 시그니처 문법부터 막힘(public RefreshRequest { return; }) → login()과 대조하며 반환타입·파라미터 자리 스스로 교정 → 본문 채우다 request.getRefreshToken() 값을 변수에 저장 안 하고 버리는 실수 지적받아 수정 → 결국 막혀서 전체 코드를 받아 타이핑, 컴파일 통과.

이번엔 "빈 채로 못 채웠다"는 결과보다 어디서 막혔는지 아는 것 자체가 소득 — 다음엔 이 지점부터 다시 시도 가능.

직접 작성

logout() — 이번엔 스스로, 실수도 스스로 발견

요구사항만 보고 refresh() 패턴 재사용해서 직접 완성. 코드리뷰에서 두 가지를 스스로 고침:

이름Logout(...) → logout(...) — 자바 메서드는 소문자 camelCase
예외InvalidCredentialsException → InvalidTokenException — 로그인 실패(자격증명 문제)와 토큰 자체 문제는 의미가 다른 예외로 구분해야 한다는 걸 다시 확인
구현

컨트롤러 엔드포인트 연결

MemberController에 /refresh, /logout 추가. /logout은 요청 본문 없이 @AuthenticationPrincipal Long memberId로 필터가 SecurityContextHolder에 심어둔 인증 정보를 그대로 꺼내 씀 — 필터·컨트롤러·SecurityContext가 실제로 연결되는 지점.

테스트

전체 시나리오 최종 통과

signup → login → refresh (새 accessToken 발급)
logout (Authorization 헤더로 필터 인증 통과) → 204
로그아웃 후 같은 refreshToken 재사용 시도 → 401 (DB에서 무효화 확인)

서브프로젝트 1번(도메인 모델 + 인증) API 4개 전부 구현 완료.
